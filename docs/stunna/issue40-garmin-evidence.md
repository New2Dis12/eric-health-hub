## Reusable result contract

`SourceEvidence` version 1 is independent of the ingestion provider: provider/source identity, format, retrieval time, SHA-256 of decoded FIT bytes, optional native modality/time bounds, summary measurements, native laps, selected sensor columns/units/samples, quality/coverage and confirmation provenance. `SourceResult` returns `matched` or `unavailable` and current immutable evidence IDs/revisions. The candidate endpoint additionally returns `needs_confirmation`. This contract can accommodate a separately approved provider adapter later; **Peloton screenshot ingestion is absent**.

Native FIT session summary is used only when exactly one session message exists. Missing or multisport summaries remain empty/unknown; no summary is estimated from prescriptions, samples, lap sums or Garmin list estimates. Native lap metrics preserve their boundaries. All missing numeric values stay null; zero remains zero. Speed is the FIT sensor measurement, not verified treadmill belt speed, incline or Peloton power. Pace derived by the legacy FIT reader is excluded from persisted measurements. Cadence remains cycles/minute (running strides/minute). Oscillation and step length have explicit native millimeter attribution and normalized centimeter units; the existing decoder's sensor speed precision and selection behavior are retained. No mapping of native laps/samples to prescribed intervals is inferred.

The browser displays sourced summaries, native laps, sensor data and coverage separately from saved user-entered results. Both a fresh `/api/training/results` read and existing `get_saved_workout_results` read return the same durable evidence envelope and IDs. Existing result-page/response byte bounds apply; reduce the MCP result page size if its existing 128 KiB response guard is reached. SQL append-only revisions plus audit events preserve past evidence; normal result reads expose the latest revision. Source corrections do not rewrite user entries, notes, prescriptions, start/completion times, status or session revision. Reads first check optional source-table existence and SELECT privileges without issuing failing SQL. Migration-008 databases, missing runtime grants and rollback from 009 retain their existing browser/MCP results contract with source status unavailable; enabled, granted migration 009 returns saved source evidence normally.

## Storage, authorization and correction policy

Migration 009 proposes two additive tables in the **existing** `stunna` schema/database: immutable `source_links` enforce one athlete/provider/activity identity and one provider association per completed session; append-only `source_evidence_revisions` retain extracted versions. Composite foreign keys bind both tables to the same athlete. FORCE RLS uses the existing authenticated subject and athlete policy. Runtime grants are SELECT/INSERT only; no UPDATE/DELETE or ownership. The revision trigger checks completed status and matching provider/source/version. Existing audit and idempotency tables are reused. No second training database or service is created.

Both feature flags `STUNNA_ENABLED` and `GARMIN_MCP_ENABLED` must already be true for vendor operations. All services enforce the exact Auth0 subject allowlist. Candidates require `training.read`; confirmation requires `training.read` **and** `training.write`; API tokens also require existing `garmin.read` from the same verified bearer. Browser sessions use the existing single-owner Garmin permission boundary and configured-origin CSRF check. Saved evidence is now training data under the existing `training.read` reader. Legacy Oura/Garmin MCP authorization and tool names remain intact. New scoped tools exist only within `/mcp`: `get_workout_garmin_candidates` and `confirm_workout_garmin_activity`. Their instructions require explicit owner confirmation; a caller assertion cannot independently prove conversational consent.

The same idempotency key and normalized command returns its original receipt, including through a Garmin outage. Different input with that key conflicts. Under the athlete transaction lock, current session and evidence revisions must match exactly. Refreshing **the same** source identity appends extracted evidence and one audit event. Another session cannot claim that activity. Replacing/relinking a session's Garmin identity is rejected deterministically with 409; there is no destructive unlink/reassignment operation in this slice. Any identity repair requires an owner-reviewed follow-on, preserving history and duplicate protections. Transaction failure rolls back the identity, evidence, audit and receipt together. The browser parses the receipt UUIDs/session/revision and requires the expected next evidence revision. It compares a fresh authenticated result with the exact completed session, Garmin source ID and confirmation ID. Equal revisions require the exact immutable evidence ID; a newer revision of that same source can supersede the receipt. Missing, older, different-source or contradictory readback retains the exact confirmation and idempotency key. The pending command clears only after this reconciliation or a definitive client rejection.
